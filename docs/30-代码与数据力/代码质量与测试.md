# 代码质量与测试

## 适用场景

代码只有你能看懂；改一个函数坏三个地方；队友接手要重写；答辩现场演示崩了。

## 最小做法

### 结构

```text
project/
├─ src/            # 源码
├─ tests/          # 测试
├─ data/           # 数据（raw/processed）
├─ configs/        # 配置
├─ scripts/        # 一次性脚本
└─ README.md
```

- 一个文件只做一类事。
- 函数短小，输入输出明确。
- 配置和代码分离，不要把路径/密钥写死。
- 入口文件只做参数解析和调用，不写业务逻辑。

### 命名

- 变量名说清含义：`motor_speed` 而不是 `a`。
- 函数名用动词：`load_data`、`compute_rmse`。
- 常量全大写：`MAX_RETRY`。
- 避免拼音缩写和无关梗。

### 注释

- 注释写“为什么”，不写“是什么”。
- 复杂公式写来源和假设。
- TODO 写清“谁、什么时候、做什么”。
- 不要用注释屏蔽大段死代码，直接删（Git 有历史）。

### 日志

```python
import logging

logging.basicConfig(level=logging.INFO, format="%(asctime)s %(levelname)s %(message)s")
logging.info("loaded %d rows", len(df))
logging.warning("missing values: %d", df.isna().sum().sum())
```

- 关键步骤有日志。
- 错误日志带上下文，不要只打“failed”。
- 不要用 `print` 做正式日志。

### 单元测试

```python
import unittest
from src.metrics import rmse

class TestMetrics(unittest.TestCase):
    def test_rmse_zero(self):
        self.assertEqual(rmse([1, 2], [1, 2]), 0)

    def test_rmse_positive(self):
        self.assertAlmostEqual(rmse([1, 2], [2, 4]), 1.5811, places=3)
```

- 每个核心函数至少一个正常用例 + 一个边界用例。
- 测试不依赖本机路径和网络。
- 提交前跑一遍。

## 进阶做法

- 用 `pytest` 替代 `unittest`，参数化测试。
- 用 `ruff`/`flake8` 做静态检查，`black`/`ruff format` 统一格式。
- 用 `mypy` 做类型检查。
- 用 CI 跑测试，PR 不通过不合并。
- 用 `coverage` 看覆盖，但不要追求 100%。
- 用 `pre-commit` 在提交前自动检查。

## 常见坑

- 一个文件几千行，函数几百行。
- 变量名 `a`、`b`、`tmp`，一周后自己看不懂。
- 注释写“这里加 1”，没说为什么。
- 测试只测“能跑”，不测边界。
- 日志打一堆，关键错误没上下文。
- 代码里写死本机路径/密钥。
- 没有 README，队友不知道从哪运行。

## 自检清单

- [ ] 目录结构清晰，源码/测试/数据分开。
- [ ] 函数短小，命名能看懂。
- [ ] 注释解释“为什么”。
- [ ] 关键步骤有日志。
- [ ] 核心函数有测试，含边界用例。
- [ ] 提交前跑测试/静态检查。
- [ ] README 写清安装、运行、测试命令。

## 版本与时效

本文基于 Python 3.11、pytest 8、ruff 0.8。工具会变，但“结构清晰 + 命名可读 + 测试覆盖核心逻辑”的原则不变。
