# 做对了什么，做错了什么

## 适用场景

你想知道别人踩过哪些坑，少走一点弯路；或者你刚做完一个项目，想对照着复盘。

## 做对了什么

### 1. 先做能演示的最小闭环

不管是机械、电控还是软件，先让“输入—处理—输出”跑通，再谈性能、外观、扩展。很多项目不是输在想法，是输在截止前没有能演示的东西。

### 2. 把交付物写死

每次分工都写到“文件/演示/测试记录”，不写“负责某模块”。交付物写死，才知道谁卡住、卡在哪。

### 3. 提前读评分表

评分表不是提交后才看的。先抄下来，逐项找证据，缺什么补什么。比“我觉得做得好”有用。

### 4. 保留失败证据

失败的照片、日志、测试数据，答辩时主动说。评委更愿意相信一个知道边界的人，而不是只讲成功的人。

### 5. 文档和代码留痕

决策记录、周报、提交历史，平时觉得麻烦，复盘/答辩/交接时救命。

## 做错了什么

### 1. 题目太大

一开始想做“平台”，结果连一个场景都没做透。后来才明白：题目越小，越容易做完；做完再扩。

### 2. 技术堆砌

为了“看起来厉害”，堆了一堆技术，但没有一个能验收。评委问“具体解决了什么”，答不上来。

### 3. 分工靠默契

以为大家关系好就不用写清楚，结果有人做得多、有人消失，最后署名/进度都尴尬。

### 4. 忽视格式和截止

材料内容不错，但页数超了/命名不对/上传太晚，直接出局。规则不是建议，是门槛。

### 5. 不记录过程

测试数据只有截图，环境/版本/命令都没记。过两周自己都复现不了，答辩被问细节就慌。

### 6. 用熬夜补进度

短期能顶，长期效率越来越低，错误越来越多。时间预算没算清楚，最后所有事都挤在一起。

## 如果重来一次

1. 题目压缩到一句话，先做最小闭环。
2. 组队第一天写清分工、交付物、退出机制。
3. 先把评分表变成检查清单。
4. 每周留一次复盘，不等到最后。
5. 所有测试记录环境、版本、命令。
6. 给关键节点留 20% 缓冲。
