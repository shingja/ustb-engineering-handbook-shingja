# 原型与实验

## 适用场景

你要把方案做成能演示的东西；一上来就想做完整系统，结果截止前只完成一半；测试记录缺失，答辩说不清数据。

## 最小做法

### 先做“能演示的最小闭环”

最小闭环 = 输入 → 处理 → 输出 → 可见结果。

- 机械：一个机构能完成一个动作。
- 电控：一个传感器能读数，一个执行器能动作。
- 软件：一条命令能跑通主流程。
- 系统：端到端能走一遍，哪怕很粗糙。

先让闭环跑通，再谈性能、外观、扩展。

### 迭代节奏

- 一周一个可演示版本。
- 每个版本记录：改了什么、为什么、结果如何。
- 版本号 `v0.1`、`v0.2`，不要“最终版”。
- 每次迭代保留上一版，出问题能回退。

### 测试

| 测试类型 | 目的 | 记录 |
|---|---|---|
| 功能测试 | 主流程能不能走通 | 步骤、预期、实际 |
| 边界测试 | 极端输入/条件 | 输入、结果、是否崩溃 |
| 性能测试 | 速度/精度/稳定性 | 指标、样本量、环境 |
| 用户测试 | 别人能不能用 | 任务、耗时、反馈 |

测试记录要能复现：环境、版本、命令、数据。

### 成本

- BOM：元件、数量、单价、来源。
- 加工：工时、外协费用。
- 时间：每个人每周投入小时数。
- 迭代损耗：打样/返工次数。

成本不是只算钱，也算时间。

### 失败证据

保留失败的照片、日志、测试数据。答辩时主动说“这个方案试过，失败的原因是……”，比只讲成功更可信。

## 进阶做法

- 用“功能—成本—风险”三维评估每个方案。
- 关键模块做两个备选，主方案失败能切换。
- 用仿真/小样先验证，再做实物。
- 每次测试写“测试计划”，不要随手试。
- 用视频记录演示过程，防止现场翻车。
- 给原型加“故障恢复”步骤：断电/重启/重置。

## 常见坑

- 一上来做完整系统，截止前没有可演示的东西。
- 只测成功路径，边界一碰就崩。
- 测试记录只有截图，没有环境/版本。
- 原型靠一根线/一个临时补丁撑着，现场必翻车。
- 成本只算采购，不算加工和时间。
- 失败记录全删，答辩被问“你们试过什么”答不上来。
- 没有备选方案，主方案失败就结束。

## 自检清单

- [ ] 有一个能演示的最小闭环。
- [ ] 每周一个可演示版本。
- [ ] 每个版本有变更记录。
- [ ] 功能/边界/性能测试有记录。
- [ ] 测试环境、版本、命令可复现。
- [ ] 成本算了钱和时间。
- [ ] 保留了失败证据。
- [ ] 关键模块有备选方案。

## 版本与时效

本文的原型方法不依赖具体技术栈。实验安全、设备规范以实验室/学校要求为准。
